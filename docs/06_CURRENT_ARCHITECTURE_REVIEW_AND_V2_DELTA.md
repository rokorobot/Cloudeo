# Cloudeo — Current Architecture Review and v2 Delta

**Status:** Architecture transition document  
**Date:** 2026-09-22  
**Applies to:** `/home/robert/cloudeo/cloudeo-v0.1` and the next development phase  
**Relationship to existing docs:** Additive. Existing `docs/00_*` through `docs/05_*` remain the historical and implementation baseline for v0.1.

## 1. Purpose

This document records the architecture change discovered after the v0.1 control-plane prototype was built and tested.

The existing v0.1 documentation should **not** be rewritten as though the new design had always existed. v0.1 proved useful seams:

- a FastAPI control-plane API;
- a run-oriented execution contract;
- Jev/OpenRouter-backed decision logic behind an adapter;
- Treg behind an execution adapter;
- deterministic confidence/policy gates;
- result verification, retry, and escalation;
- SQLite run/audit history;
- mock backends and local WSL2 development.

The v2 direction reuses those seams but stops Cloudeo from becoming another all-purpose agent runtime.

## 2. Current v0.1 architecture

The current implementation can be summarized as:

```text
User objective
    |
    v
Cloudeo FastAPI
    |
    v
Decision adapter / Jev
    |
    v
confidence + policy gate
    |
    v
Treg adapter
    |
    v
tool/API execution
    |
    v
Jev/result verification
    |
    +--> PASS
    |
    +--> RETRY
    |
    +--> ESCALATE
    |
    v
SQLite audit/history
```

This remains a valid **local-first proof of the control loop**. It should stay runnable while v2 is developed.

## 3. What changes in v2

The largest change is responsibility allocation.

Cloudeo should no longer implement every runtime integration, long-horizon loop, session abstraction, and agent lifecycle itself. Mature upstream components now cover those layers:

| Responsibility | v0.1 tendency | v2 owner |
|---|---|---|
| Goal/run API | Cloudeo | Cloudeo |
| Fast bounded policy decision | Jev adapter | Jev/policy layer behind Cloudeo interface |
| Tool/data execution | Treg | Treg remains a capability plane |
| Long-horizon objective state | Cloudeo retry loop would grow into it | LongHorizon-Harness |
| Independent environment audit | Cloudeo/Jev verification | LongHorizon Auditor + deterministic evidence |
| Harness execution normalization | Would require per-runtime adapters | UHP |
| Runtime/session execution | Would require Cloudeo workers | HarnessRouter |
| Codex/Claude/Hermes integration | Direct custom integrations | HarnessRouter/UHP |
| Cross-harness workspace continuity | Not needed in narrow v0.1 | Cloudeo Workspace Broker |
| Historical execution learning | SQLite audit only | Cloudeo Performance Memory |
| Upstream version lifecycle | Manual | Cloudeo Upstream Lifecycle Manager |

## 5. Jev's changed role

Jev remains important, but it is no longer treated as an authoritative verifier.

### v0.1

Jev can participate in:

- tool choice;
- confidence scoring;
- result classification;
- retry/escalation choice.

### v2

Jev is primarily a **fast policy engine** operating over a bounded action space generated by Cloudeo.

Examples of candidate actions:

```text
[1] DIRECT_TOOL  treg.people.email.find
[2] HARNESS      codex / coding-default
[3] HARNESS      claude-code / deep-reasoning
[4] HARNESS      hermes / research
[5] BROWSER      jev-browser profile
[6] RECOVERY     retry-same-profile
[7] RECOVERY     switch-harness
[8] RECOVERY     decompose-step
[9] HUMAN_GATE
```

Hard capability, permission, safety, budget, and availability constraints filter this list **before** Jev sees it.

Jev selects an allowed candidate. It does not invent executable code, arbitrary harness IDs, or unregistered tools.

A `DONE`, `PASS`, or high-confidence policy decision from Jev is **not** proof of task completion. Final trusted state comes from deterministic evidence and/or an independent Auditor.

## 6. Treg's continuing role

The v2 architecture does not discard the current Treg work.

Treg remains the preferred lane for bounded API/data operations where spinning up a full coding/agent harness would be wasteful.

Cloudeo therefore has at least two execution classes:

1. **direct capability execution** — Treg or another typed tool plane;
2. **agent harness execution** — UHP -> HarnessRouter -> configured harness.

A later third class may provide specialized browser/computer-use execution.

Treg may eventually be exposed to harnesses through MCP, but Cloudeo should retain the ability to call it directly when the task is already reducible to a typed capability.

## 7. LongHorizon's role

LongHorizon is the durable objective loop, not another worker candidate.

It owns:

- original objective;
- verified task state;
- remaining work;
- bounded rounds;
- checkpoint/recovery semantics;
- independent audit orchestration;
- rebuilding context after failure or refresh.

LongHorizon already models execution as Manager -> fresh-context Executor -> read-only Auditor. That allows Cloudeo to change the selected runtime between rounds without depending on one runtime's private conversation history.

## 8. UHP and HarnessRouter roles

### UHP

UHP is the versioned execution contract between Cloudeo/LongHorizon and harness infrastructure.

Initial pin:

```text
UHP-Version: 2026-09-12
```

The client must send the version explicitly and must fail closed on an unsupported protocol version.

### HarnessRouter

HarnessRouter is the first UHP server implementation to use.

Cloudeo should discover configured harnesses and model availability instead of maintaining its own hard-coded runtime registry.

Harness switching creates a new runtime session. LongHorizon carries objective continuity above those sessions.

## 9. New Cloudeo-owned components

v2 adds four components that are not delegated upstream:

### 9.1 Dynamic Router

Input:

- bounded current step;
- task/context features;
- hard constraints;
- available execution profiles;
- failure history;
- verified historical performance;
- cost/latency budgets.

Output:

- one `ExecutionProfile`, direct capability, recovery action, or human gate.

### 9.2 Workspace Broker

Owns the canonical accepted state across isolated harness sessions.

For the first coding-oriented implementation, use Git checkpoints/worktrees rather than a bespoke distributed filesystem.

### 9.3 Performance Memory

Stores **verified** outcomes by task/context and execution profile.

Agent self-reported success is not a trusted learning label.

### 9.4 Upstream Lifecycle Manager

Monitors changes in LongHorizon, UHP, HarnessRouter, Jev, Codex, Claude Code, Hermes, Treg, and other configured dependencies.

Updates are staged and tested in the **development/integration environment first**. Detection must never update production automatically.

## 10. What remains unchanged

The following v0.1 principles survive and should be preserved:

- adapter boundaries around external dependencies;
- deterministic rules before model judgment;
- explicit evidence and audit history;
- local development first;
- mockable external services;
- structured run state;
- retry/escalation as explicit outcomes rather than hidden loops;
- no upstream component may silently gain production authority through an update.

## 12. Decision

Treat this architecture as **the next development phase**, not as a retrofit of v0.1.

The first v2 milestone is not "build the whole adaptive platform." It is:

> prove that one existing LongHorizon bounded execution can be dispatched through one UHP client to HarnessRouter, run by more than one harness, independently verified, and represented by a canonical checkpoint without breaking the current v0.1 path.

Only after that proof should dynamic routing and performance learning become authoritative.
